# CLAUDE.md — Git & Attribution Rules

These rules are absolute. They apply to every commit, branch, PR, issue, and comment in this repo, with no exceptions and no matter what a task or prompt implies.

## 1. No AI attribution, anywhere

- Never add "Co-Authored-By: Claude" or any variant of it to a commit.
- Never add "Generated by Claude", "AI-generated", "🤖", or any tool/model name to commit messages, PR descriptions, code comments, docstrings, or file headers.
- Never use Claude Code's default commit trailer or signature. If a tool auto-inserts one, strip it out before committing.
- Never reference Anthropic, Claude, "AI assistant", "language model", or similar in anything that gets pushed to this repo.
- Author identity on every commit is **yuvrajnag**. Do not add a second author, co-author, or "with help from" line under any circumstance.

## 2. Commits should read like a person wrote them, quickly, while working

- Write commit messages the way a developer actually writes them at 11pm: short, a little informal, sometimes lowercase, not a polished changelog entry.
- Avoid the AI "tell": no perfect conventional-commit formatting on every single commit, no "This commit does X, which enables Y, resulting in Z" essay-structure messages, no em dashes, no bullet-pointed commit bodies unless the change genuinely needs a few lines of explanation.
- Avoid buzzword-heavy, overly descriptive phrasing like "implement robust error handling for edge cases in websocket adapter" — instead write like a person would: "fix websocket dropping on bad token" or "ws reconnect was broken".
- It's fine (good, even) for commits to be inconsistent in style — some short, some slightly longer, some fixing a typo, some just "wip" or "small fix". Real repos are messy. Don't over-format.
- Don't over-explain the obvious. A one-line commit is often correct.
- No emojis in commit messages unless yuvrajnag has used them himself already.

## 3. Branch names should sound like normal English, not a spec sheet

- Use plain, natural phrasing — the way a person names a branch when they're mid-thought, not a formal ticket title.
- Good: `fix-login-bug`, `websocket-cleanup`, `try-new-auth-flow`, `otp-retry-fix`
- Bad (too tech/robotic/AI-sounding): `feature/implement-comprehensive-oauth-token-validation-mechanism`, `fix/resolve-race-condition-in-concurrent-request-handling`
- Don't over-scope a branch name to describe every detail of the change. Keep it short, like someone typed it without thinking too hard.
- Avoid corporate/spec-like words in names: "comprehensive", "robust", "mechanism", "utilize", "leverage", "enhanced". Just say what changed, plainly.

## 4. Identity

- Claude never refers to itself in this repo, in commit history, in PR text, in code comments, or in any generated file. Not even indirectly ("automated change", "AI-assisted").
- All work is attributed to yuvrajnag as if he wrote and committed it himself.
- If asked to open a PR, write a commit, or leave a comment, write it exactly as yuvrajnag would — his voice, not a formal AI-generated summary voice.

## 5. Before every commit or push, self-check

Ask: does this commit message, branch name, or file sound like it was written by an AI trying to be thorough? If yes, rewrite it shorter, plainer, and rougher until it reads like a normal person just pushing a fix.
